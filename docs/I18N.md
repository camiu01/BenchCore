# Interface language (English and Italian)

BenchCore renders its interface in English or Italian. Post content is never
translated: the language only affects interface text, API messages and dates.

## How the language is chosen

1. The `lang` cookie, if it holds `en` or `it`.
2. The browser's `Accept-Language` header, using quality weights and ignoring
   regional suffixes (`it-IT` selects `it`).
3. English.

The cookie is set only when a visitor presses a language button. It is first
party, `HttpOnly`, `SameSite=Lax`, valid for one year, and `Secure` on HTTPS.
The `POST /language` endpoint stores it and redirects (303) to the `return`
field. Only same-site absolute paths are accepted; anything else returns to `/`.

## Frontend

- `frontend/src/lib/i18n/locale.ts` negotiates the language.
- `frontend/src/lib/i18n/messages/<area>.en.ts` and `<area>.it.ts` hold the
  catalogs. The Italian file is typed against the English keys, so a missing
  translation fails `pnpm check`. Keep `{name}` placeholders identical.
- Svelte components use `t('area.key', { name })` from `i18n/t.svelte.ts`.
  Loaders and form actions use `serverT(...)` from `lib/server/server-t.ts`.
- `hooks.server.ts` stores the language in `event.locals.locale`, sets
  `<html lang>` and runs the request inside an `AsyncLocalStorage` so
  `lib/server/transport.ts` can send `Accept-Language` to the API.

## API

`api/src/i18n/` mirrors the negotiation (cookie, then header, then English) and
renders the messages in `messages.ts`. Responses keep their machine-readable
`error` code, so clients must branch on `error`, never on `message`. Zod
`issues` and CLI output stay English diagnostics.

## Adding a language

1. Add the code to `LOCALES` and `LOCALE_NAMES` in `locale.ts` and the API
   `ApiLocale` type.
2. Add the catalogs for every area. TypeScript reports each missing key.
3. Add the Intl tag in `intlTag` and run `pnpm test`.
